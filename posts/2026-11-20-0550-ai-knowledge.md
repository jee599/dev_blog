The bug showed up as a spreadsheet problem. My nightly pipeline summarizes long PDFs with Claude and writes one row per document. One morning, document 4471 had two summaries. Slightly different wording, start times 61 minutes apart, same Celery task ID.

Same task ID is the part that made my stomach drop. That isn't a retry. That's the broker handing the exact same message to a second worker while the first one was still chewing on it. The cause was Celery visibility_timeout on the Redis broker, and over 14 nights it quietly ran 214 of my 1,380 jobs at least twice.

## TL;DR

- On the Redis (and SQS) broker, Celery's `visibility_timeout` defaults to **3600 seconds**. Any message a worker has taken but not acknowledged within that hour gets pushed back onto the queue and delivered again.
- With `acks_late=True`, a task isn't acknowledged until it finishes. Any task that runs longer than an hour gets **redelivered while it's still running**.
- Prefetch makes it worse: messages sitting in a worker's prefetch buffer are also unacknowledged. Short tasks queued behind long ones can hit the hour without ever starting.
- Fix: raise `visibility_timeout` above your longest task plus queue wait, set `worker_prefetch_multiplier = 1`, and add an idempotency guard per job.
- Trade-off: a higher timeout means a task lost in a real worker crash waits that long before it's retried.

## What does Celery visibility_timeout actually do?

Celery visibility_timeout is how long the Redis transport waits for an acknowledgement before assuming the worker died and putting the message back on the queue. Redis has no native concept of "this consumer has this message," so Kombu fakes it.

When a worker reserves a message, Kombu copies it into an `unacked` hash with a timestamp. When the task is acknowledged, the entry is removed. Kombu periodically scans that hash, and anything older than `visibility_timeout` gets restored to the queue as if it had never been delivered.

That's a reasonable design for crash recovery. It just has no idea the difference between "the worker died" and "the worker is on minute 73 of a big PDF."

## My setup

Nothing exotic:

- 2 worker boxes, `--concurrency=4` each, prefork pool
- Redis as broker, Postgres for results and job state
- Each job: split a PDF into chunks, summarize each chunk with Claude, then merge into a final summary
- Runtime: most jobs 4 to 15 minutes, a long tail of 60 to 110 minutes for big documents
- `acks_late=True` on the task, because I wanted a crashed job to come back

That last line is the one I'd written with pride. "If a worker dies mid-job, the job gets retried. Very robust." It was robust in exactly the way that bills you twice.

## How I found 214 duplicate runs

Every job writes a `job_runs` row when it starts, keyed by Celery's `task_id`. A real retry gets a new row with the same task ID too, so I couldn't just count rows. I needed runs that **overlapped in time**:

```sql
SELECT a.task_id, count(*) AS runs
FROM job_runs a
JOIN job_runs b
  ON a.task_id = b.task_id
 AND a.id <> b.id
 AND a.started_at < coalesce(b.finished_at, now())
 AND b.started_at < coalesce(a.finished_at, now())
WHERE a.started_at > now() - interval '14 days'
GROUP BY a.task_id;
```

Results for the 14 nights:

| Metric | Count |
|---|---|
| Jobs dispatched | 1,380 |
| Jobs that ran at least twice | 214 |
| Of those, ran three times | 9 |
| Duplicates from long runtime (`acks_late`) | 171 |
| Duplicates from waiting in prefetch | 43 |

The second run almost always started 60 to 62 minutes after the first. That gap is the fingerprint. If you see duplicates clustered at exactly your timeout plus a little scan lag, stop looking for a bug in your code.


## Why did tasks longer than one hour run twice?

Tasks longer than one hour ran twice because `acks_late=True` delays the acknowledgement until the task returns, so the message stays in Redis's `unacked` hash for the whole runtime. At the 3600-second mark, Kombu restores it and another worker picks it up.

Here's the part that scared me more than the duplicates. When the first run finally finishes and acks, it doesn't cancel the restored copy. That copy is a fresh delivery with its own timer. If the second run *also* takes more than an hour, it gets restored again. In principle a 70-minute job loops forever.

Mine didn't, and not because of anything clever. My pipeline caches chunk summaries in Postgres. The second run found the chunks the first run had already finished and skipped them, so it was usually faster. The 9 triple runs were the biggest documents, where even the cached rerun crossed the hour.

So the only thing standing between me and an infinite loop of paid API calls was a cache I'd added for a completely unrelated reason.

## Why did short tasks get duplicated too?

Short tasks got duplicated because prefetched messages count as unacknowledged, even when they haven't started. With the default `worker_prefetch_multiplier = 4` and concurrency 4, each worker box reserves up to 16 messages at once.

Picture a box where all 4 processes grab big documents that take 90 minutes. The 12 messages sitting behind them in the prefetch buffer are reserved, not started, and their timer is running. At 60 minutes they get restored, the other box runs them, and 30 minutes later the original box runs them too.

These 43 were the expensive ones. A long job's duplicate partly hit the chunk cache. A prefetched short job's duplicate ran from scratch in parallel on another machine, full price, no cache hits.


## What did the duplicates cost?

Across the 14 nights, the duplicate runs consumed about 23 million input tokens on the Claude API. That was roughly 11% of the pipeline's total input tokens for the period. Not a catastrophe, but it was 11% of the bill buying literally nothing, plus two summaries per document that my downstream code had to dedupe.

The less visible cost: every duplicate occupied a worker slot, which pushed more jobs into the prefetch buffer, which created more prefetch duplicates. The bug fed itself on busy nights. My worst night had 31 duplicates; my quietest had 4.

## How do you fix Celery visibility_timeout on Redis?

You fix it by setting `visibility_timeout` longer than your longest possible task plus its worst queue wait, cutting prefetch to 1 for long tasks, and making the task itself idempotent. Here's the config before and after:

```python
# before
app.conf.task_acks_late = True
# visibility_timeout: default 3600
# worker_prefetch_multiplier: default 4

# after
app.conf.task_acks_late = True
app.conf.worker_prefetch_multiplier = 1
app.conf.broker_transport_options = {
    "visibility_timeout": 12 * 3600,  # 12h, longest job is ~2h
}
```

Put this in the shared config module that every process imports: workers, beat, and the web app that calls `.delay()`. The restore scan can run from any client connected to the transport, and you don't want one process quietly using the 1-hour default.

Then the seatbelt, because config drifts and someday someone will add a 14-hour job:

```python
@app.task(bind=True, acks_late=True)
def summarize_doc(self, doc_id: int):
    if db.job_is_done(doc_id):
        return  # a duplicate delivery after success

    key = f"summarize:{doc_id}:lock"
    if not redis_client.set(key, self.request.id, nx=True, ex=6 * 3600):
        log.warning("duplicate delivery doc=%s task=%s", doc_id, self.request.id)
        return

    try:
        run_pipeline(doc_id)
        db.mark_done(doc_id)
    finally:
        redis_client.delete(key)
```

The `done` check catches redeliveries after a successful run. The `SET NX` lock catches concurrent ones. The lock TTL is your crash escape hatch: if a worker dies holding it, the job is blocked for at most 6 hours.

## Did the fix work?

Yes. Over the next 14 nights, 1,302 jobs ran with 0 overlapping duplicates, and the idempotency guard logged 0 skips. Zero skips is what I want to see: the guard isn't doing the work, the config is. The guard is there for the day I'm wrong about the longest job.

I also tested the failure path on staging with `visibility_timeout` temporarily set to 5 minutes and a `kill -9` on a worker mid-job. The job came back after about 5 minutes and ran once. In production that same scenario now means a 12-hour wait, which I'm fine with for a nightly batch. For a user-facing queue, I'd split long jobs into a separate queue with its own timeout instead.

## What I'd tell myself before turning on acks_late

1. **`acks_late` and `visibility_timeout` are one setting.** Never touch one without the other.
2. **Your timeout budget is runtime plus queue wait**, not just runtime. Prefetch is queue wait you can't see in Flower.
3. **Same task ID, overlapping runs, ~60 minutes apart** is a diagnosis, not a mystery.
4. **LLM tasks are the worst case.** They're long, they're variable, and every duplicate is real money.
5. **Idempotency isn't optional** on any queue that promises at-least-once delivery. Redis-backed Celery promises exactly that.

## So why did my Celery jobs run twice on Redis?

My Celery jobs ran twice because the Redis broker's `visibility_timeout` defaults to one hour, and any message not acknowledged within that hour is put back on the queue for another worker. With `acks_late=True`, every job longer than 60 minutes crossed that line while still running, and with the default prefetch of 4, short jobs waiting behind long ones crossed it without ever starting. That added up to 214 duplicate runs out of 1,380 and about 11% wasted input tokens. Raising `visibility_timeout` to 12 hours, setting `worker_prefetch_multiplier = 1`, and adding a per-job idempotency lock brought duplicates to zero over the next 1,302 jobs.
