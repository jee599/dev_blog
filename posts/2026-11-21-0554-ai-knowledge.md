I planted one number in a vector of 4,096 floats. I set it to 60, quantized the vector to INT4 with absmax scaling, and looked at what was left.

All 4,095 of the other values were exactly zero.

Not "a bit noisy." Zero. The whole row went down to one integer level, plus the outlier. That one experiment explains most of what goes wrong in LLM quantization: why per-tensor INT4 is never shipped, why GPTQ and AWQ default to `group_size=128`, and why bitsandbytes has a `llm_int8_threshold=6.0` knob that most people never touch.

This post walks through **absmax quantization**, the outlier failure mode, and the three fixes real libraries use. Everything here ran on my laptop with numpy, and the script is short enough to paste.

## TL;DR

- **Absmax quantization** sets one scale per block: `scale = max(|x|) / qmax`. The largest value in the block decides the step size for every other value.
- One outlier of 60 in 4,096 standard-normal values pushed the INT4 step to 8.57. Everything with `|x| < 4.29` rounds to 0, so **4,095 of 4,096 values became zero**.
- INT8 survives better but still breaks: the same outlier left the normal values only **16 distinct levels out of 255**, and relative error went from 0.89% to 13.78%.
- The fix is to stop sharing a scale with the outlier: **group-wise scales** (e.g. 128 values per scale), **mixed-precision decomposition** (LLM.int8), or **moving the outlier's magnitude into the weights** (SmoothQuant).

## What is absmax quantization, exactly?

Absmax quantization maps floats to signed integers using one scale per block: divide by `max(|x|) / qmax`, round, and clip. For INT8, `qmax = 127`. For INT4, `qmax = 7`.

```python
import numpy as np

def absmax(v, bits):
    qmax = 2 ** (bits - 1) - 1          # 127 for int8, 7 for int4
    scale = np.abs(v).max() / qmax      # one number for the whole block
    q = np.clip(np.round(v / scale), -qmax, qmax)
    return q, q * scale                 # ints, and the dequantized floats
```

That's it. It's symmetric, cheap, and it's the starting point for nearly every quantization scheme you've used. The weakness is sitting right there on the `scale` line. One `max()` decides the ruler for everybody.

## Why does one outlier break absmax quantization?

Because the step size is `max / qmax`, and any value smaller than half a step rounds to zero. If one value is 15x bigger than the rest, the step grows 15x and the "dead zone" around zero swallows the rest of the block.

Here's my setup. 4,096 values drawn from a standard normal (seed 0), so the natural max was about 3.9. Then I set index 7 to 60.0 and compared.

| Setup | Step size | Normal values rounded to 0 | Distinct levels used | Relative error |
|---|---|---|---|---|
| INT8, per-tensor, clean | 0.031 | 1.1% | 191 | 0.89% |
| INT8, per-tensor, outlier = 60 | 0.472 | 17.8% | 16 | 13.78% |
| INT4, per-tensor, clean | 0.557 | 20.8% | 14 | 16.22% |
| INT4, per-tensor, outlier = 60 | 8.571 | **100%** | **1** | **100%** |

Relative error is measured on the 4,095 normal values only, so the outlier doesn't flatter the numbers.

Read the INT4 row slowly. The step is `60 / 7 = 8.57`. Half a step is 4.29. Not a single one of my 4,095 Gaussian values was larger than 4.29 in magnitude, so every one of them rounded to 0. The outlier is preserved perfectly. Everything else is gone.

The INT8 row is sneakier. It *looks* fine if you only check that the tensor dequantizes without NaNs. But your 255-level integer grid now spends 239 levels on a range only the outlier lives in. The normal values get squeezed into 16 levels.


## What does this do to the actual matmul?

It biases the dot product, not just the stored values. Quantized activations feed a matrix multiply, so I took a random weight vector and computed the dot product with the 4,095 normal values before and after quantization.

- True contribution from the normal values: **-19.22**
- After INT8 with the outlier: **-8.96** (more than half the signal lost)
- After INT4 with the outlier: **0.00** (all of it)
- After INT8 on the clean vector, for reference: -19.82

So the outlier's own term still lands correctly, but the 4,095 "boring" dimensions stop contributing. In a real transformer those boring dimensions are most of the hidden state. The model doesn't crash. It just gets dumber in ways that show up as worse perplexity or weird generations, and you go hunting for a bug in your prompt template.

## Do LLMs really have outliers like this?

Yes, and that's the well-known part of this story. The LLM.int8() paper (Dettmers et al., 2022) reported that once models get to the multi-billion-parameter range, a small number of hidden-state feature dimensions carry values far larger than the rest, and those dimensions show up consistently across layers and tokens. They're called emergent outlier features, and the paper argues they matter for model quality, so you can't just clip them.

My planted 60 is a toy. The shape of the problem is the real thing: a handful of huge values in a sea of small ones, sharing one scale.

## How do you fix absmax quantization outliers?

You stop letting the outlier set the scale for values it has nothing to do with. There are three standard ways to do that.

### Fix 1: group-wise scales (what GPTQ, AWQ and llama.cpp do)

Split the tensor into small groups and give each group its own absmax scale. The outlier can only ruin its own group.

```python
def absmax_grouped(v, bits, group=128):
    out = [absmax(g, bits)[1] for g in v.reshape(-1, group)]
    return np.concatenate(out)
```

Same vector, same outlier, groups of 128:

| Setup | Normal values rounded to 0 | Distinct levels | Relative error |
|---|---|---|---|
| INT8, group 128, outlier | 1.4% | 249 | 2.58% |
| INT4, group 128, outlier | 17.4% | 15 | 20.34% |
| INT4, group 128, clean | 14.7% | 15 | 11.53% |

The damage didn't disappear, it got fenced in. Inside the group that holds the outlier, INT4 still zeroed all 127 neighbors. The other 31 groups were untouched, which is why the totals look close to the clean run.

This is the reason `group_size=128` shows up as a default in GPTQ and AWQ configs, and why llama.cpp's quant formats store a scale per small block. The cost is storage: one extra scale per group. At 128 values per FP16 scale, that's 16 extra bits per 128 weights, about 0.125 bits per weight. For INT4 that's a small price for not deleting entire rows.


### Fix 2: pull the outliers out (LLM.int8 mixed precision)

LLM.int8() does matrix decomposition: any activation feature above a threshold gets computed in FP16, and everything else goes through the INT8 path. In bitsandbytes this is the `llm_int8_threshold` setting, default 6.0.

```python
from transformers import BitsAndBytesConfig

cfg = BitsAndBytesConfig(load_in_8bit=True, llm_int8_threshold=6.0)
```

I did the crude version of this on my vector: set the outlier aside, quantize the rest to INT8, put the outlier back in full precision. Relative error on the normal values: **0.89%**, identical to the clean run. Makes sense. Once the outlier leaves the block, the scale goes back to what the 4,095 normal values need.

The tradeoff is speed. You now run two matmuls and stitch them together, which is why 8-bit bitsandbytes inference is often slower than FP16 on the same GPU. You're trading throughput for memory and accuracy.

### Fix 3: move the scale into the weights (SmoothQuant)

SmoothQuant (Xiao et al., 2022) handles activation outliers by dividing each activation channel by a per-channel factor and multiplying the matching weight row by the same factor. The matmul result is mathematically identical, but the activation outliers shrink and the weights, which are easier to quantize, absorb the difference. A migration strength `alpha` (0.5 is the common starting point) controls how much difficulty moves from activations to weights.

Use this when you want both weights and activations in INT8 (W8A8) with a single fast integer matmul, which mixed decomposition can't give you.

## How do I check my own quantized model for this?

Measure the ratio of max to typical magnitude per block before you pick a scheme. If `max(|x|) / median(|x|)` is huge for some blocks, per-tensor absmax will crush them.

```python
def outlier_report(t, group=128):
    g = t.reshape(-1, group).abs()
    ratio = g.max(dim=1).values / g.median(dim=1).values.clamp_min(1e-8)
    return ratio.max().item(), (ratio > 20).float().mean().item()
```

Run it on a layer's weights, and on activations captured with a forward hook over a few real prompts. Then check how many dequantized values came back exactly 0 that weren't 0 before. That count is the cheapest smoke test I know, and it would have caught my INT4 row instantly: 4,095 new zeros.

## So why did one outlier zero 4,095 of 4,096 values in INT4 absmax quantization?

Because absmax quantization uses a single scale per block, `max(|x|) / qmax`, and INT4 has only 7 positive levels. An outlier of 60 made the step 8.57, so any value under 4.29 in magnitude rounded to zero, and in a block of standard-normal values that's all of them. The fix is to never let an outlier share a scale with normal values: use group-wise scales (128 values per scale is the common default), split outliers into a higher-precision path like LLM.int8 does, or migrate activation outliers into the weights with SmoothQuant. If you're picking a quantized checkpoint, check its group size before you check its bit width.
