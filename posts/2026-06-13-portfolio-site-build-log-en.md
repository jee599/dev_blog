1,492 tool calls across 13 sessions in two days. One of those sessions ran 532 tool calls over 27 hours and 48 minutes. The output: a photography portfolio site, a Korean astrology global service, a coffee chat / mentorship platform admin and payment system, and a dental clinic briefing deck — all shipped (or near-shipped) in the same 48-hour window, by one developer.

This isn't a post about AI being magic. It's a post about what actually breaks when you push an agentic coding setup to its limits, and what you learn from hitting the session limit four times in two days.

**TL;DR:** Multi-agent orchestration with five parallel sub-agents, a hard design gate enforced by shell hooks, and disciplined state management via files made it possible for one person to run four projects simultaneously. Session limits hit four times. Concurrent edit collisions happened. The enforced design system gate saved more time than it cost.

---

## When a session hits 532 tool calls, structure isn't optional

Session 11 was the longest. 532 tool calls, 27 hours 48 minutes of wall-clock time, all spent on a Korean astrology service that needed a complete UI overhaul plus localization into 7 locales.

At that scale, the thing that kept the session coherent wasn't willpower or good prompting — it was structure. Specifically: `/effort ultracode` to activate the dynamic workflow mode, and a pattern of spinning up five parallel sub-agents, each scoped to a single deliverable.

The five parallel workstreams in that one session:

1. Landing page redesign ("Midnight Almanac" theme)
2. Loading screen casting sequence animation
3. Paywall page
4. Report output page
5. Translation pipeline for 7 locales

None of these agents shared context directly. That's the thing people don't fully internalize about parallel agents: **they're isolated processes**. Any shared state has to be a file with a known path passed explicitly in each sub-agent's prompt. If you hand-wave that detail, you get agents that contradict each other's work.

The pattern that worked:

```
# In each sub-agent prompt:
"Shared state is at /project/agents/state.json.
Read it first. Write your changes back when done.
Do not assume you know what other agents produced."
```

It's not elegant, but it's explicit, and explicit beats implicit when you're running five parallel processes.

## 293 photos, one collision, and a fullscreen slideshow

The daymoon photography site relaunch started with a photo inventory. 293 images across multiple categories. The first step before writing a line of code was having Claude enumerate the catalog, then choosing a design direction from five options generated by the Open Design skill.

The direction chosen: "White Curation" — a minimal, gallery-style aesthetic. Full-width hero slideshow cycling through 12 representative images with a crossfade transition. Dynamic gallery grid below, filterable by category. Clean admin panel with three tabs: photo upload, booking inbox, and seasonal settings.

Session 6, 216 tool calls, roughly 10 hours.

The interesting technical piece was Vercel Blob storage integration. Photography sites live or die on image quality, and any system that downsizes originals at upload time is a problem. The integration allowed direct upload of originals up to 50MB, with CDN delivery from Vercel's edge. The admin tab handles upload, tagging, and category assignment in one flow.

Then the collision happened.

I was running a second session in parallel — working on a different project in a different terminal window, same repository on disk. Session A wrote a component. Session B, unaware of that write, read the stale version, modified it, and wrote back. Session A's changes were gone.

The error message was blunt: `"Concurrent session overwrote OK files."`

The fix isn't complicated — use git worktrees for parallel same-repo sessions, or at minimum commit between context switches. But it's the kind of thing you only learn by losing work once.

```bash
# The right way to run parallel sessions on the same repo
git worktree add ../portfolio-site-session-b -b session-b-work
# Each session gets its own working directory
# No file collisions
```

For the daymoon session, I recovered from git history. The collision cost about 40 minutes.

## The Etsy natural experiment and a payment platform rejection

The Korean astrology service had a problem before any design work started: getting a payment platform approved for fortune-telling content is harder than you'd expect.

The category itself triggers review flags on most payment processors. Divination, fortune-telling, astrology readings — these hit content policy edge cases at Stripe, PayPal, and others. Not outright rejections in every case, but the review process is slow and unpredictable.

While waiting on payment approvals, I ran a search for natural experiment data on how this category actually performs. The Etsy data was striking: one shop that branded itself as "AI Reading" — foregrounding the algorithmic nature of the service — ran for a month and got 0 sales. A comparable shop that used a human persona and framed readings as personal, human-crafted work ran for a year and got 464 sales.

That's not a controlled experiment, but it's directionally clear: the framing of the service matters as much as the content, and "AI-generated" is currently a liability in this specific category.

The design direction responded to this. The "Midnight Almanac" theme: deep ink indigo background, gold hairline accents, Fraunces serif typeface. A `three.js` star drift animation as the cosmic background — subtle particle movement, not a flashy effect. The goal was to feel like an artifact rather than a SaaS product.

```javascript
// three.js star field setup — minimal, not a showpiece
const stars = new THREE.Points(starsGeometry, starsMaterial);
stars.rotation.x = Math.PI / 2;
scene.add(stars);

// Slow drift on the z-axis only
function animate() {
  requestAnimationFrame(animate);
  stars.position.z += 0.01;
  if (stars.position.z > 50) stars.position.z = 0;
  renderer.render(scene, camera);
}
```

GPT Image 2 was running in the background generating atmospheric images while the UI code was being written in parallel. This worked fine, but it required careful file naming conventions so the image generation agent and the UI coding agent didn't step on each other's asset paths.

Mid-session, feedback came in: "The rotating saju chart looks childish." The chart was a SVG element with a CSS rotation animation — it looked fine in isolation but clashed with the dark, serious visual language of the rest of the page. It came out. Static display of the same information looked better immediately.

The session hit the limit twice during this work. The second time was at a bad point — mid-way through the translation pipeline, with three locales done and four remaining.

The recovery pattern: before any long agentic session, write the current project state to a memory file.

```markdown
# project_saju_paypal.md

## Current Status (2026-06-12)
- Payment platform: PayPal application pending review (submitted 2026-06-11)
- Fallback: Stripe with manual content review flag acknowledged
- UI: Midnight Almanac theme — complete
- Locales complete: ko, en, ja
- Locales remaining: zh-TW, zh-CN, fr, es
- Known issues: hero image on mobile needs srcset update
```

When the session limit hit, starting fresh with this file as context meant the new session picked up without manual re-explanation. The lesson: treat project state files as session checkpoints, not just documentation.

## 20 slides became 13, and "AEO/CPC" became "37,000 won per click"

The dental clinic briefing deck started as a 20-slide presentation covering digital marketing performance — search ad efficiency, local SEO rankings, click-through rates across channels.

The first feedback after sharing the draft: "It's hard to follow just from the slides."

This is a common problem with technical reports handed to non-technical stakeholders. The data is accurate. The charts are correct. But the cognitive load of parsing AEO, CPC, CTR, and impression-share data across 20 slides, without a narrator, is too high.

The revision approach:

1. Cut from 20 to 13 slides. Anything that required context from another slide to be meaningful got merged or removed.
2. Replace every metric abbreviation with a plain-language equivalent in the slide itself, not in the speaker notes. If the audience is reading without a presenter, the slide has to carry the explanation.
3. Limit each slide to fewer than half the number of figures the original had. Dense numbers make people stop reading. The slides that survived kept one or two headline numbers, large, with everything else supporting those.

"AEO/CPC" became: "One click from a featured snippet costs approximately 37,000 KRW — about 4x higher than standard search ads."

That's a worse metric to optimize for if you're a performance marketer. It's a better piece of information if you're a clinic director deciding how to allocate budget.

The technical work here was minimal — slide editing in a structured format. The cognitive work was deciding what to cut and how to reframe what remained. Two sessions: session 1 (175 tool calls) for the initial build, session 7 (82 tool calls) for the revision pass.

## The design gate that blocked my own HTML files

One of the reasons the visual work across these projects held together was a hard gate in the local Claude Code setup. This isn't a Claude feature — it's a shell hook.

The setup:

```bash
# hooks/design-gate.sh
# Runs as a pre-tool-use hook in Claude Code
# Blocks writes to .html/.htm files unless the session
# has been explicitly marked as an Open Design pass

if [[ "$TOOL_NAME" == "Write" || "$TOOL_NAME" == "Edit" ]]; then
  if [[ "$FILE_PATH" =~ \.(html|htm)$ ]]; then
    if [[ ! -f "$PROJECT_ROOT/.claude/design-pass-active" ]]; then
      echo "BLOCKED: HTML write requires an active Open Design session."
      echo "Run hooks/design-pass.sh to acknowledge this session as a design pass."
      exit 1
    fi
  fi
fi
```

```bash
# hooks/design-pass.sh
# Creates the flag file that unlocks HTML writes for this session
touch "$PROJECT_ROOT/.claude/design-pass-active"
echo "Design pass acknowledged. HTML writes are now unblocked for this session."
```

The rule encoded in `CLAUDE.md`: any HTML deliverable — landing pages, report outputs, email templates, dashboards — has to go through the Open Design skill before it's considered done. The hook enforces this mechanically. You can't accidentally ship a Claude-generated HTML file that skipped the design system pass, because the file write is blocked until you explicitly acknowledge the session as a design pass.

This sounds bureaucratic. In practice, it caught two instances in these two days where I was about to write a "quick" HTML file for a project component without thinking about whether it matched the established design system. The gate forced a five-minute check. Both times, the quick version would have looked inconsistent.

The other hook in the chain is `hooks/protect-files.sh`, which blocks writes to `.env*` files and credential paths. Simple, but essential when running high-volume agentic sessions where a stray write to a secret file is a real possibility.

## Three things ultracode taught me in 48 hours

**1. Parallel agents don't share context — design around that, not against it.**

The instinct when spinning up multiple agents is to write rich natural-language context in each prompt and hope they stay consistent. They won't. Shared state needs to be a file with a defined schema, at a path you pass explicitly. Treat it like an API contract between processes. Each agent reads the file at start, writes its changes at end, and makes no assumptions about what other agents have done.

```
# Practical pattern
agents/shared-state.json    # canonical project state
agents/agent-1-output/      # agent 1 writes here only
agents/agent-2-output/      # agent 2 writes here only
# Orchestrator merges from output dirs into shared-state.json
```

**2. Session limits correlate with wall-clock time, not just tool call count.**

I expected session limits to be primarily about token usage or tool call volume. The 532-call session hitting the limit after 27+ hours suggests there's a time component. Long-running sessions that span natural sleep/work cycles are more likely to hit limits than intensive but short sessions with similar call counts.

The practical implication: for any session expected to run more than a few hours, set up checkpoints. A checkpoint is a git commit plus a state file write. Recovery from a checkpoint takes 10 minutes. Recovery from a limit-hit mid-task without checkpoints takes 45 minutes to an hour, depending on complexity.

**3. "Continue" is a more powerful prompt than it looks.**

After a limit-hit or a break, the prompt to resume wasn't a detailed re-explanation of the current state. It was `"Continue."` — with the state file in context. Claude reconstructed task lists, identified what was incomplete, and resumed from the right point. The state file did the heavy lifting. The single-word prompt just triggered execution.

This suggests that the bottleneck in long-horizon agentic work isn't the model's ability to pick up context — it's whether the context is written down in the first place. Externalize state as a first-class concern, not an afterthought.
