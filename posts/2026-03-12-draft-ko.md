하루에 커밋 8개, QA 3라운드, 보안 구멍 2개, 결제 공급자 긴급 롤백 1번 — 43개 파일이 바뀐 날이었다.

3월 10일의 작업 로그를 꺼내보면 이렇게 돼 있다. 커밋 타임스탬프가 새벽부터 자정 직전까지 촘촘하게 찍혀 있다. 기획한 게 아니었다. 하나를 고치면 다른 곳에서 뭔가가 튀어나오는 날이 있는데, 그게 이 날이었다.

나는 사주(四柱, Four Pillars of Destiny) AI 리포트를 판매하는 앱을 혼자 만들고 있다. 한국 전통 명리학을 AI로 해석하고, 결과를 구매할 수 있는 구조다. 타로, 궁합(커플 사주), 손금 분석까지 붙어 있고, 한국어·영어·일본어·힌디·태국어·인도네시아어·베트남어·중국어로 8개 로케일을 지원한다. 결제는 국내용 Toss와 글로벌용 Paddle을 분리해서 운영한다.

그날은 원래 간단한 일을 하려고 시작했다.

## 궁합 페이지가 너무 가벼웠다

궁합 기능의 원래 버전은 출생 시간을 받지 않았다. 사주 계산에서 출생 시간(시주, 時柱)은 네 기둥 중 하나인데, 이걸 하드코딩으로 정오(noon)로 고정해 두고 있었다. "일단 만들고 보자"식으로 넣은 코드가 그대로 남아 있던 거다.

게다가 리포트 섹션이 4개뿐이었다. 오행 분석, 궁합 점수, 관계 특성, 종합 조언. 그 정도면 콘텐츠가 너무 얇아서 5,900원(원래 3,900원이었다)을 받기 어렵다는 판단이 섰다. Claude에게 한 줄짜리 지시를 던졌다.

> "compat 페이지에 출생 시간(12지지 선택) 입력 추가. 사주 엔진에 실제 시간 반영. 리포트 6섹션으로 확장. 가격 ₩3,900→₩5,900."

응답이 한 번에 왔다. 출생 시간을 고르는 드롭다운 UI, 엔진에 시간 값을 전달하는 로직 수정, LLM 프롬프트를 3개 청크로 나눠서 병렬로 실행하는 구조, 8개 로케일에 새로 필요한 i18n 키 전부. 커밋 하나(4f9c985)로 들어갔다. 검토하는 데 15분쯤 걸렸다. 새 섹션은 communication — 두 사람이 일상에서 어떻게 소통하는지 — 과 timing — 관계에서 좋은 시기와 조심할 시기 — 이었다. 섹션이 늘어나면 LLM 응답 대기 시간이 길어지는데, 병렬 청크 구조로 체감 속도를 유지했다.

이때까지는 순조로웠다.

## 1라운드: 숨어 있던 일관성 버그들

궁합 개편을 올리고 나서, 지금까지 쌓인 기능 전체를 한 번 훑어보기로 했다. Claude에게 전체 앱을 읽히면서 명백한 버그를 찾아달라고 했다. 코드베이스 전체를 컨텍스트로 넘기는 방식이다.

1라운드에서 나온 것들은 주로 일관성 문제였다(커밋 2fe4e2c). 헤더 컴포넌트가 페이지마다 `sticky`와 `fixed` 포지션을 섞어 쓰고 있었다. 스크롤하면 페이지마다 동작이 달랐던 이유가 이거였다. `error.tsx`와 `not-found.tsx` — Next.js의 에러 처리 페이지들 — 에 i18n이 아예 없었다. 한국어로 보면 한국어 텍스트, 힌디어로 보면 동일한 한국어 텍스트가 나오는 상태. API 에러 메시지 몇 개도 한국어 하드코딩이었다. 영어권 사용자가 결제 실패 시 한국어 에러를 받는 구조.

공유 카드 UI에서도 숫자 검증이 빠져 있었다. 점수가 0~100 범위를 벗어날 수 있는 케이스가 있었고, LINE 공유 링크가 모바일에서 깨지는 버그도 잡혔다. 전부 이 라운드에서 처리했다. 솔직히 혼자 보면 못 잡았을 것들이다. 내가 만든 화면은 내가 보면 잘 보인다고 착각하기 때문이다.

## 2라운드: 보안 구멍이 두 개 나왔다

2라운드(커밋 123f515)는 분위기가 달랐다. "HIGH QA fixes"라는 커밋 메시지를 쓴 날이다.

첫 번째는 타로 paywall이었다. 타로 결과의 일부는 무료로 보여주고, 전체 해석은 유료다. 근데 paywall 코드가 `alert()`를 쓰고 있었다. 브라우저 기본 alert 창. 모바일에서는 특히 더 이상해 보인다. 이걸 커스텀 모달로 바꿨다. 단순 UI 이슈처럼 보이지만, alert이 막히는 브라우저 환경도 있고 UX 측면에서도 제품 신뢰도에 영향을 준다.

두 번째가 더 심각했다. 내부 API 엔드포인트가 헤더 스푸핑에 열려 있었다. 서버 간 통신에만 쓰이는 `/api/*` 경로들이 있는데, 이게 외부에서 `x-internal-secret` 헤더만 붙이면 접근이 됐다. 검증 코드가 없었던 거다. Claude가 이걸 찾아냈을 때, 나는 솔직히 그냥 지나쳤을 것 같다는 생각을 했다. 보안 리뷰를 전문으로 하지 않는 이상 이런 게 눈에 잘 안 들어온다. 비밀 환경변수가 하드코딩 fallback을 갖고 있던 것도 이 라운드에서 제거했다.

홈 폼에서 `useRef`로 이중 제출을 방지하는 로직도 들어갔다. 사주 계산은 LLM을 쓰기 때문에 더블 클릭 한 번에 두 배 비용이 나간다.

## Toss 결제를 붙이고 바로 긴급 롤백했다

결제 얘기를 해야 한다. 가장 아찔했던 부분이다.

Toss Payments 연동을 완성했다(커밋 2c58ca3). 웹훅 처리, 결제 영수증 이메일, 8개 로케일 × 5개 상품 조합 전부. 이 작업은 며칠에 걸쳐서 진행됐고, 3월 10일에는 최종 확인 단계였다.

근데 QA 3라운드(커밋 121086b)에서 문제가 나왔다. 한국어 결제가 Toss로 라우팅되고 있었는데, Toss 구현이 아직 미완이었다. `paymentProvider: 'toss'` 설정이 코드에 들어가 있었지만 실제 결제 플로우가 완성되지 않은 상태. 즉, 한국어 사용자가 결제 버튼을 누르면 실패하는 상태였다.

발견 즉시 Paddle로 롤백했다. 커밋이 두 개 생겼다. `fix: restore Korean paymentProvider to toss (critical)`라고 메시지를 썼는데, 나중에 다시 보니 이건 Paddle로 롤백한 커밋이 맞다. 커밋 메시지를 잘못 썼다. 어수선한 날이었다는 증거.

`INTERNAL_API_SECRET` 환경변수에 하드코딩 fallback이 남아있던 것도 이 라운드에서 찾아서 제거했다. 보안 환경변수에 fallback이 있으면, 환경변수가 없는 환경에서 테스트할 때 취약점인지도 모르고 넘어간다.

## 타로 공유 기능과 카피 실험

타로 결과 공유 기능이 없었다. 사주(四柱) 결과는 공유 버튼이 있는데 타로는 빠져 있었다. 구조적 누락이었다. 이걸 추가하면서 share landing 페이지에 티저 콘텐츠도 넣었다(커밋 9553df1). 공유 링크를 받은 사람이 페이지에 들어오면 자기 타로를 바로 해보고 싶도록 유도하는 구조다.

카피 실험이 흥미로웠다. 처음에는 공유 텍스트를 1줄로 줄이고 성격 특성 목록을 제거했다(커밋 cab0e53). 가설은 짧고 강렬한 카피가 바이럴 전환률이 높다는 거였다. SNS에서 긴 텍스트는 읽히지 않는다는 일반론이었다.

그런데 한 커밋 뒤에 바로 revert했다(커밋 ca70ae0). 이유는 직관이었다. 특성 목록이 들어간 버전 — "당신의 이번 달 주요 특성: 결단력 ★★★★, 직관력 ★★★★★..." 같은 형태 — 이 실제로 더 눈길을 끈다는 판단. 사람들은 자기 이야기가 구체적으로 써있을 때 공유하고 싶어한다.

데이터 없이 내린 결정이라 맞는지는 모른다. A/B 테스트를 돌리거나 실제 공유 후 클릭률을 보고 판단해야 한다. 그냥 "느낌"으로 revert한 거다. 이런 결정을 로그로 남겨두는 이유가 여기 있다. 나중에 검증할 기준점이 된다.

힌디어(hi) OG 이미지에서 타로 제목이 영어로 나오는 버그도 이 즈음에 잡혔다(커밋 560dc73). 힌디어 사용자가 공유하면 OG 프리뷰에 영어가 나오는 문제. 8개 로케일을 지원하면서 가장 자주 생기는 유형의 버그다. 영어를 기준으로 만들고 나머지를 번역하는 방식인데, 가끔 OG 이미지 경로 같은 "숨은 곳"이 빠진다.

## Three.js 배경 위에서의 가독성 문제

이 날은 아니었지만, 그 일주일 전(3월 5일)에 겪은 일도 같이 써둔다. Three.js 3D 별 배경을 전체 화면에 붙였더니 텍스트가 다 뭉개졌다.

CSS 변수 `--bg-card`와 `.glassCard`의 배경 불투명도가 10% 수준이었다. 정적인 다크 배경에서는 괜찮아 보였는데, 별빛이 움직이는 배경 위에서는 텍스트가 떠다니는 것처럼 보였다. `rgba(13, 11, 20, 0.72)` 계열로 올렸다. 0.10에서 0.72로.

별자리 선은 아예 잘라냈다. 3개 별자리를 연결하는 선을 그리는 코드가 36줄 있었는데, `opacity: 0.12`라 실제 화면에서 거의 안 보이면서 렌더링 비용만 쓰고 있었다. Claude에게 "별자리 선이 시각적 노이즈가 되고 있다. 삭제해줘"라고 하니 36줄이 한 번에 사라졌다. 필요 없는 코드를 과감하게 지우는 게 맞다는 걸 다시 확인했다.

사주(四柱) 결과 테이블도 손봤다. 천간(天干)과 지지(地支) 한자에 보라색 glow 효과를 넣고, 행 구분선을 추가했다. 한자가 작은 글씨로 빽빽하게 나오면 처음 보는 사람에게 위압감을 줄 수 있다. 약간의 시각적 계층을 넣는 것만으로 읽히는 느낌이 달라진다.

파비콘도 이 날 추가했다. Next.js App Router는 `app/icon.svg`를 자동으로 파비콘으로 등록한다. 별도 설정 없이. Claude에게 "Next.js App Router 방식으로 파비콘 추가해줘"라고 했더니 올바른 경로와 SVG 코드를 10줄로 줬다. 보라→시안 그라디언트 별 아이콘.

## Claude로 QA를 돌리는 방식

여기서 작업 방식을 좀 설명하고 싶다.

QA를 Claude에게 위임하는 방식이 나한테 맞는다는 걸 이번에 다시 확인했다. 방법은 간단하다. 코드베이스를 전부 읽힌 다음 "전체 앱을 훑어서 명백한 버그, 불일치, 보안 이슈 목록을 뽑아줘"라고 한다. Claude는 내가 직접 클릭해서 확인하는 것보다 범위가 훨씬 넓다.

내가 직접 QA를 하면 "내가 방금 만든 기능"을 중심으로 보게 된다. 엣지 케이스를 놓친다. 다른 페이지와의 일관성을 놓친다. 3달 전에 넣어둔 코드를 잊어버린다. Claude는 이 패턴에서 자유롭다. 파일 시스템 전체를 동등하게 본다.

물론 한계도 있다. Claude는 실제로 앱을 실행하지 않는다. UI를 직접 보지 않는다. 그래서 시각적인 문제 — Three.js 배경에서 텍스트가 뭉개지는 것 같은 — 는 스크린샷을 붙여줘야 잡힌다. 로직 버그와 UI 버그의 발견 방식이 다르다는 걸 인식하고 있어야 한다.

이번 주에 나온 QA 결과 중 가장 좋았던 건 보안 이슈 발견이었다. Internal API 헤더 검증 누락과 환경변수 하드코딩 fallback. 이런 건 기능 테스트에서는 안 나온다. 코드 리뷰에서 잡히는 유형인데, 나 혼자 개발하면 자기 코드를 리뷰할 사람이 없다. Claude가 그 역할을 부분적으로 채워주고 있다.

## 숫자로 정리

3월 10일 하루를 숫자로 정리하면 이렇다. 커밋 8개, 변경 파일 43개, 추가된 코드 640줄, QA 라운드 3회, 발견된 보안 이슈 2개, 긴급 롤백 1회, 추가된 i18n 키 12개, 결국 revert된 바이럴 카피 실험 1회.

가격도 바뀌었다. 궁합 리포트가 ₩3,900에서 ₩5,900으로 올랐다. 리포트 섹션이 4개에서 6개로 늘었고, 출생 시간까지 반영하는 더 정교한 계산이 들어갔다. 콘텐츠가 늘어났으니 가격도 맞춰야 한다는 단순한 논리다. 이 판단이 맞는지는 실제 구매 데이터가 나와야 안다.

## 런칭 직전 QA를 이렇게 돌리는 게 맞는가

솔직히 모르겠다. 하루에 QA 3라운드를 돌리면서 커밋을 8개 쌓는 방식이 효율적인지, 아니면 그냥 체계가 없는 건지.

장점은 명확하다. 어디서 무엇이 변했는지 커밋 단위로 추적이 된다. 롤백도 쉽다. 실제로 이날 결제 공급자를 롤백할 때 30초도 안 걸렸다. 커밋이 잘게 쪼개져 있었기 때문이다.

단점은 컨텍스트 스위칭 비용이다. 궁합 개편을 하다가 QA 결과를 받고 보안 이슈를 고치다가 다시 바이럴 카피 실험을 하는 흐름. 집중이 분산된다. 깊이 들어가야 하는 작업에는 이 방식이 맞지 않는다.

런칭을 앞두고 "일단 최대한 많이 잡자"는 심리가 있는 것 같다. 런칭 후에는 사용자가 생기고 그때부터는 변경의 무게가 달라진다. 지금은 대담하게 바꿀 수 있는 마지막 시기라는 느낌이 있다. 그 심리가 이런 집중 QA 방식을 만들어낸다.

Toss 결제가 미완인 채로 한국 결제를 라우팅하고 있던 건 단순한 실수다. 두 개의 결제 공급자를 동시에 개발하면서 상태 관리가 엉켰다. 이런 실수는 CI에 결제 플로우 테스트가 있었다면 잡혔을 거다. 있었는지 확인해보니, 있었다. 근데 환경변수가 없는 CI 환경에서는 결제 테스트가 skip됐다. 테스트가 있어도 실행 안 되면 없는 거랑 같다.

이 글은 자랑이 아니라 기록이다. 잘된 것, 실수한 것, 아직 검증 안 된 것을 그대로 썼다. 바이럴 카피 revert도, Toss 긴급 롤백도, "느낌으로 결정했다"는 것도. 1인 개발은 이런 결정들의 연속이다. 데이터가 없으면 직관으로 가고, 직관이 틀리면 고친다. 그 기록이 쌓이면 나중에 더 나은 직관이 된다고 믿는다.
